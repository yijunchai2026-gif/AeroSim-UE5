# Runtime control MCP — 2026-10-17

User explicitly authorizes adding flight control to MCP and diagnosing the real keyboard/mouse failure through it. Root owns the Command API, runtime adapter, stdio transport, input correction and evidence. Existing Editor-only ScenePatch protocol remains isolated; this is a new opt-in Development-only local runtime diagnostic surface, not arbitrary scripting or production editing.

A fixed sandbox mailbox bridges JSON-RPC MCP stdio tools to the running game thread. No listener/port, remote control, arbitrary paths, reflection, console commands or code execution. A fresh runtime session ID rejects stale/cross-session requests; fixed actor `player:0`, bounded request size, expiry, idempotency and a single writer. Inspect exposes page, possession, physical neutral, pause/countdown, Enhanced Input mapping, Slate focus, actual mapped action values and pose. Key commands route through Slate's normal input entry and Enhanced Input, never assign a success pose or inject flight-model semantic values. Menu actions call the same GameMode commands as native buttons.

Writes run inspect → preview → snapshot → apply → bounded validation → before/after audit → commit or restore. Keys automatically release within 2 seconds of wall time, even while game paused; transport timeout sends release. A failed command restores opening mission/model/pose and clears held synthetic input. Scene geometry/environment are never edited. Capture calls the existing hashed pixel capture path. No settings persistence or formal asset operations are exposed. Runtime control validation is not visual G0–G4 or performance sign-off.

First build adds diagnosis, preserving the reported behavior. Use real MCP initialize/tools/list/tools/call to navigate the normal mission flow and press throttle/direction keys. Preserve failing state evidence, then repair the cause and rerun. No PASS based only on direct SetSemanticInput or debug flight-state seeding. Mouse movement must be explicitly gated for camera look; passive mouse must not steer the aircraft. Shipping disables the bridge.

## Review-view vision extension — 2026-10-18

Purpose: let a model inspect the scene through the same bridge, without OS screenshots or window activation, for faster G0→G3 iteration. Owner: root (bridge, GameMode capture, MCP transport).

- `aerosim_capture` and the new `aerosim_capture_view` return an MCP `image` block: a 1280-wide JPEG derived from the evidence PNG (Pillow, else `/usr/bin/sips`). The preview is never evidence; the PNG, its SHA256 manifest and the manifest summary stay authoritative. The server reads back only a `.png` inside the bridge's own `Saved/Screenshots/Product` root.
- `aerosim_capture_view(view, view_mode)` accepts only enum values. `view` is `player` or a preset from `AAeroSimGameMode::ResolveReviewView`, now the single pose table shared with temporal sampling (bridge uses Step 8, matching temporal `frame-023`). `view_mode` is `lit | lighting_only | detail_lighting | unlit` via `UGameViewportClient::SetViewMode`; a mode the engine refuses fails as `VIEW_MODE_UNAVAILABLE` instead of silently capturing Lit. Cooked builds reject non-Lit modes unless `r.ForceDebugViewModes=1`, but leaving that on crashes every cooked screenshot (`FSceneView::ConfigureBufferVisualizationSettings` dereferences the editor-only `r.BufferVisualizationOverviewTargets` cvar; reproduced as SIGSEGV), so the bridge sets it only around `SetViewMode` and restores it immediately. Wireframe (both `VMI_Wireframe` and `VMI_BrushWireframe`) rendered black except water in the cooked Metal build and is not offered.
- Capture waits ≥30 frames and ≥1 s after the camera cut, and up to 6 s for texture streaming (`streaming_wanting_at_capture` is reported). HUD/Slate UI are excluded. View target, HUD and view mode are restored on success, failure and EndPlay. A changed view target fails as `VIEW_TARGET_OVERRIDDEN`. No pose, path, console command or arbitrary camera is accepted.
- Both capture operations now track the exact output they started. They fail as `CAPTURE_NOT_STARTED` instead of completing on an older evidence file.
- Manifest additions: `review_view`, `view_mode`, `capture_protocol=bridge-review-view/v1`; `diagnostic_draw_calls_source`; `scene_frustum_*` geometry budget (CPU bounds test of components/instances, LOD0 triangles, no occlusion/shadow/Lumen; explicitly not draw calls).

Draw-call root cause: UE 5.8.3 `FMetalRHICommandContext::FlushProfilerStats()` is declared and defined but never called, unlike the D3D12 and Vulkan contexts. Metal draw stats are therefore never emitted to the GPU profiler and `GNumDrawCallsRHI` stays zero. `diagnostic_draw_calls` keeps its raw value so the verifier still fails closed. Real Metal draw counts require an engine change or Xcode GPU capture; a Windows D3D12 build should populate the existing counter.
